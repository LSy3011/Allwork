# ADR-006: 物理语义下沉与规格驱动 (Semantic Lowering & Spec-Driven Driver)

## 1. 现状与挑战
目前 AIACC 编译器的驱动层 (`FieldMapper`) 存在**隐式推断逻辑**。例如，通过识别算子名中的 `SUB` 关键字（如 `FPSUB`）来自动点亮硬件的 `add_sub` 或 `SUB` 比特位。这种设计导致了两个严重问题：
- **职责模糊**：算子库（如 `sin.py`）作为算法的实现者，却不能完全控制硬件行为，必须依赖后端的“黑盒推断”。
- **硬编码脆弱性**：当硬件规格（Spec）变更字段名或编码方式时，必须同时修改驱动代码，导致后端极度臃肿。

## 2. 架构决策：MLIR 式的属性映射

我们决定采用“物理属性显式化”的设计原则，将硬件行为的控制权彻底交还给算子拆分阶段（Lowering）。

### A. 物理语义下沉 (Semantic Lowering)
- **核心思想**：算子拆分阶段生成的 IR（如 `MIROp`）必须显式定义其对应的**硬件比特字段**及其语义值（如 `SUB=1`, `UPDATE_ST=0`）。
- **属性透明**：IR 不再仅仅是一个抽象的 `FPADD` 名字，而是一个包含全量硬件配置属性的“待打包指令块”。

### B. 规格驱动驱动程序 (Spec-Driven Driver)
- **核心思想**：驱动程序回归为 **Mechanical Bit-Packer（机械打包机）**。
- **打包逻辑**：
    1.  驱动加载 `unit.yaml`（真相源）。
    2.  按顺序遍历 YAML 中的 `code_fields`。
    3.  尝试从算子 `metadata` 中通过**字段名**（如 `SUB`）查找对应值。
    4.  若 `metadata` 中未显式指定，则回退到 YAML 中的 `default`。
    5.  驱动层**严禁**包含任何基于 OpName 模式匹配的补全逻辑（如 `if "SUB" in op_type`）。

## 3. 预期收益
- **硬/软解耦**：硬件字段重命名不涉及驱动代码逻辑变更，仅更新 YAML。
- **可观测性**：在 `dfg.json` 或日志中即可明确看到算子的物理行为意图中，无需进入驱动层黑盒查看。
- **测试提速**：`test_driver_sim_parity.py` 等对齐性测试将覆盖 100% 的字段物理对齐。

## 4. 实施要求
- 现有的 `FieldMapper.py` 中的 `SEMANTIC_OP` 相关硬编码分阶段移除。
- `library/atomic/` 下的所有算子模板需更新 `metadata` 以适配新的显式属性规范。
