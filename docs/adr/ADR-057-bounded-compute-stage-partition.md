# ADR-057：受限 COMPUTE 自动分段（草案）

本文固定执行方向，尚非实现或验收完成声明。遵循 ADR-004 文档先行；按已同意路线在复核后实现。硬件数值不变。

## 目标与边界

在 ADR-056 已支持的无状态、非原地更新、单输出逐元素配置中，自动拆分超过 128 行的计算程序。首证 scale_sum，单 SMC、无反压、顺序执行；数据在 UR 内驻留。保留单 stage 路径和指令字节。

区分三层：COMPUTE 分段解决 IQ 容量；LOAD/COMPUTE/STORE 表达阶段依赖；host chunk 解决工作集容量。未来程序可以是 LOAD → COMPUTE_0 → … → COMPUTE_k → STORE，并非固定三个 stage。

非目标：本轮不实现 LOAD/STORE、LSU 进入 SMT、归约/累加状态、矩阵、原地更新、多 SMC、chunk、ragged tail、换入换出和流水重叠。M3-lite 后续独立复核变延迟完成契约，不复用计算 ISSUE 模型。

## 对 ADR-056 既有闸门的修订（2026-09-30 复核补记）

本 ADR 修订两处 ADR-056 冻结契约。实现时按新形态落码，**不得静默删除防御性闸门**：

1. **G-stage（ADR-056 §B.2-7）**：现闸门 `src/driver/assembler.py:127` 拒绝一切 `stage_id∉{None,0}`（src 尚无 stage_id 生产者，系契约虚设闸门，其 docstring 本就注明"未来出现 stage 切分元数据即在此响亮拒绝，诊断指向 A2a"）。修订为：拒绝**计划外** stage_id——凡不在本次运行 manifest stage 集合内的 stage 元数据，仍按原形态响亮拒绝（STATIC_ADMISSION_REJECTED/G-stage）。
2. **G-cap 与分段器的先后关系**：容量超限时，属本 ADR 范围的请求先交分段器；分段器拒收（非目标形态、不足以容纳一次完整迭代、数据布局不支持等）才落原 G-cap 响亮拒绝。范围外请求的 G-cap 拒绝行为零变化。

## D1：统一逻辑迭代切分

使用所有相关 IQ 的容量约束共同求每段可执行迭代数；等长满段加尾段。scale_sum 的 60 次迭代上限仅是当前案例，不作为全局常量。

对当前段长 m，候选行数 L_q(m)=II_q*(m+span_q)+2；最终以重新生成的每个队列实际行数校验。专用或压缩路径必须用其实际行数规则，不能套此公式。不能容纳一次完整迭代则明确拒绝。

所有 stage 的半开区间 [start,end) 必须精确覆盖 [0,N_eff)，无重叠、遗漏或空段。数据布局界独立检查，IQ 分段不能扩大 bank 容量。

## D2：按段重新发射

重建每段 INIT、槽序列、填充/排干和 TERM，禁止切割已编码 hex。定义局部重复号 p、op 偏移 r_k、段起始 s：逻辑全局迭代 j=s+p-r_k；LIVE 为 s≤j<end；地址按 orig_offset+stride*j 计算。驻留 stride=0 保持原址。

LIVE 未取模地址先检查张量声明区；FILL/DRAIN 按 ADR-056 受控读契约处理。所有写事件须属于本段有效输出区；不能以终值恰好相同豁免重复或越界写。

## D3：程序 manifest

机器可读文件随每次 run 归档并计入 SHA256SUMS。最少字段：schema_version、输入配置/有序 AST/调度/硬件配置/协议模型哈希、总迭代数；每段 stage_id、kind=COMPUTE、前置段、迭代区间、地址偏移（明确 word/byte 单位）、active_smc、IQ 文件与哈希/实际行数、期望写区、completion_contract_id。

manifest 是生成产物，不是独立真值。检查器从原始任务重算覆盖及地址范围，对照 manifest、解码指令和 RTL 事件。测试同时覆盖未重封印篡改与重新计算哈希后的语义篡改，防止只验证哈希。漏段、重复段、偏移错误、错误写区均须 RED。

## D4：执行与段间完成

复用 TB 顺序装载、触发、等待完成并应答机制；UR 持久性作为已有设施前提。等待中断不自动证明排干：首证必须记录各段末笔实际写回、完成/应答和下一段启动，验证先后关系以及无跨段残留写。

设计实现时明确 stage 边界事件的信号/日志来源和全局 cycle；不能根据期望事件数量猜切段。数据搬运阶段未来另定义完成契约，尤其 STB 外部写完成与 LDB 实际落位。

## D5：打包、裁决与发布

复用 package_vcs_case.py 的 stage 参数；添加多段遍历与一致性检查。注意 clean=True 会清理整个 case，不能每段重复清理；输入和最终 golden 只初始化一次。

期望在 VCS 前按 stage 生成、绑定协议版本；按真实 stage 边界对账，保留公共时间轴和段间检查。当前 unroll 模型仅适用其已证边界，未建模反压/形态不能报 GREEN。

独立目录执行；全部 stage 和最终独立参考验证通过才发布。原有单段入口行为与指令兼容；报告元数据可新增版本字段，不要求带时间戳报告逐字节一致。

## 验收与顺序

1. 复核本草案，最小生成两段 n=244，真实 VCS 侦察段间完成/写回/地址；未接入正式链前仅记实验。侦察必须点名覆盖**尾段形态**：n=244 尾段仅 1 次逻辑迭代（FILL/DRAIN 主导、运行于高地址区 j∈[60,61)），其 INIT/FILL/DRAIN/TERM 事件形态须与协议注册表 v2（冻结自单段程序 n=4/8/60）逐一对账；n=480（60+60 无尾段）为天然对照。
2. 完成统一入口和 stage 裁决：n=244（60+1 次迭代）、n=480（60+60）正式验收，段长以实际计划复核。
3. 单段代表规模 n=4/8/60/240 指令对冻结基线双向零字节差异；不声称仅测四点即穷尽所有 n≤240。
4. 对抗：漏段、重复段、偏移一格、超容量、提前完成/跨段写、未支持数据布局；失败不发布。
5. add/mul 既定回归、pytest、独立数值比对、最终/非目标区域与实际写事件检查；保留新旧证据。

## 后续 M3-lite 与两个月安排

中期前：第1周最小两段，第2周统一验收，第3周缓冲/新结构预检，第4周冻结与报告。已有 V1 不重做。

中期后：第5周新结构与限时 STB 侦察，第6周争取单 chunk M3-lite，第7周巩固实验，第8周冻结及论文。STB 与公式验证按实际人力、许可证和沙箱占用排队，不默认免费并行。

M3-lite 三道门：预置 UR 的 STB 独验 → 外部输入真正落 UR 的 LDB 复核 → 输入仅在外部存储的完整组合。不得预置正确 UR 数据绕过 LOAD。多 chunk/8 SMC 尾块/上板不属于最低交付。

第3周末仍有阻断则冻结中期范围，以 V1 为已完成成果；第6周搬运有重大阻断则评估转向 8 SMC 代表验证，不同时承诺两条开放主线。论文从现在同步写。
